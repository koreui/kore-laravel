# Internacionalización (i18n)

**TL;DR**: el **español es el idioma fuente** — las vistas escriben `__('Iniciar sesión')`
con el texto español como clave y `APP_LOCALE=es` la devuelve tal cual. El **inglés es el
fallback** y vive en JSON: `lang/en.json` para lo compartido y
`app/Modules/{Modulo}/Resources/lang/en.json` para cada módulo. `tests/Feature/TranslationsTest.php`
falla si añades un texto sin traducir.

---

## La decisión: español como fuente

El boilerplate ya nació con la UI escrita en español dentro de `__()`:

```blade
<h1>{{ __('Bienvenido de vuelta') }}</h1>
```

Antes de esta guía el proyecto corría con `APP_LOCALE=en`. Como no existía ningún
`lang/en.json`, `__()` devolvía la clave literal y la UI salía en español… pero las
**validaciones y los mensajes de Fortify salían en inglés** (`auth.failed`,
`validation.required`). Media pantalla en cada idioma.

La corrección es coherente en vez de invasiva:

| | Antes | Ahora |
| --- | --- | --- |
| `APP_LOCALE` | `en` | **`es`** |
| `APP_FALLBACK_LOCALE` | `en` | `en` |
| `APP_FAKER_LOCALE` | `en_US` | **`es_ES`** |
| UI (`__('texto')`) | español (clave devuelta) | español (clave devuelta) |
| Validación / auth / passwords | inglés | **español** (`lang/es/*.php`) |
| Inglés | no existía | `lang/en.json` + JSON por módulo |

**Por qué las claves en español siguen funcionando con `es`**: no hay `lang/es.json` con
esas claves, así que `Translator::get()` no las encuentra, intenta resolverlas como
`grupo.item` (tampoco existe `lang/es/Bienvenido de vuelta.php`) y termina devolviendo la
clave. Es el mismo mecanismo que ya usaba el boilerplate con `en`, sólo que ahora el
locale coincide con el idioma de las claves.

> ⚠️ **No hay fuga de inglés**: Laravel 12 sólo carga el JSON del locale activo
> (`$this->load('*', '*', $locale)`). Si una clave falta en `es.json` **no** se busca en
> `en.json`; el fallback JSON no existe. Por eso añadir `lang/en.json` no cambia nada de
> lo que ve un usuario con `APP_LOCALE=es`.

## Dónde va cada cosa

```
lang/
├── en.json                  # inglés de resources/views (layouts, landing, componentes)
├── es.json                  # SÓLO claves cuyo literal está en inglés (ver abajo)
├── en/                      # php artisan lang:publish — referencia
│   ├── auth.php  pagination.php  passwords.php  validation.php
├── es/                      # traducción completa de lo anterior
│   ├── auth.php  pagination.php  passwords.php  validation.php
└── vendor/one-time-passwords/es/   # correo y textos del OTP en español

app/Modules/{Modulo}/Resources/lang/
└── en.json                  # inglés de ese módulo (Auth, Users, Tenancy)
```

Cada `{Modulo}ServiceProvider::boot()` registra el suyo con **una línea**:

```php
$this->loadJsonTranslationsFrom("{$base}/Resources/lang");
```

Laravel mezcla todos los JSON del locale con
`array_merge($jsonPaths, $paths)` (`Illuminate\Translation\FileLoader::loadJsonPaths()`):
primero los de los módulos, **`lang/` al final**. Consecuencia práctica: si una clave
está en el JSON de un módulo y en `lang/en.json`, **gana la de `lang/`**, así que la app
siempre puede sobreescribir el texto de un módulo sin tocarlo.

Los módulos duplican a propósito las claves genéricas que usan (`Guardar`, `Cancelar`,
`Contraseña`…): un módulo se copia a otro proyecto con sus textos completos. Para que las
copias no se separen, el test falla si la misma clave se traduce de dos formas distintas.

### Claves cuyo literal está en inglés → `lang/es.json`

Hay mensajes que llegan en inglés porque los emite el framework o un paquete, no el
boilerplate. Son la excepción a "el español es la fuente" y se traducen al revés: la clave
inglesa vive en **`lang/es.json`** con su texto español. Hoy son tres familias:

| Origen | Ejemplo de clave |
| --- | --- |
| Correos de Laravel (`VerifyEmail`, `ResetPassword`, plantilla `mail::message`) | `Verify Email Address`, `Hello!`, `Regards,`, `All rights reserved.` |
| Respuestas de Fortify | `The provided two factor authentication code was invalid.` |
| El propio `UpdateUserPassword` del boilerplate | `The provided password does not match your current password.` |

Sin esto, con `APP_LOCALE=es` la app se ve en español pero **los correos de verificación y
de reset salen íntegros en inglés**: era el agujero más visible del setup anterior.

> El último caso es el único que está en nuestras manos: si algún día ese literal se
> reescribe en español dentro del Action, se mueve su traducción de `lang/es.json` a
> `app/Modules/Auth/Resources/lang/en.json` y listo.

> Las dos primeras familias **no** las ve el escáner del test: viven en `vendor/`. Si
> actualizas Laravel o Fortify y aparece un texto nuevo en inglés en un correo, se añade
> aquí a mano; lo que sí hace el test es renderizar el correo de verificación completo y
> fallar si vuelve a colarse un `Hello!` o un `All rights reserved.`.

## Cómo añadir un texto nuevo

1. Escribe el texto **en español** dentro de `__()`:
   ```blade
   {{ __('Exportar usuarios') }}
   ```
2. Añade su traducción al inglés en el JSON que le toque:
   - texto de un módulo → `app/Modules/{Modulo}/Resources/lang/en.json`
   - texto compartido (`resources/views`, layout, landing) → `lang/en.json`
3. `./vendor/bin/pest tests/Feature/TranslationsTest.php`

Si te lo saltas, el test falla listando la clave y el archivo donde la escribiste:

```
Hay 1 clave(s) __() sin traducir.
  · "Exportar usuarios"  ← app/Modules/Users/Resources/views/pages/index.blade.php
```

**Con placeholders** usa siempre `:nombre`, nunca interpolación:

```php
__('Hola, :name', ['name' => $user->name])   // ✅
"Hola, {$user->name}"                        // ❌ no se puede traducir
```

## Cómo añadir un idioma nuevo (p. ej. portugués)

1. `lang/pt.json` con las claves compartidas y
   `app/Modules/{Modulo}/Resources/lang/pt.json` con las de cada módulo — mismas claves
   españolas, valores en portugués. No hay que tocar ningún provider: la línea
   `loadJsonTranslationsFrom()` registra el **directorio**, no un locale.
2. `lang/pt/{auth,pagination,passwords,validation}.php` copiando `lang/es/` y traduciendo.
   Mantén las claves idénticas.
3. Si usas magic links, `lang/vendor/one-time-passwords/pt_PT/` ya viene con el paquete.
4. Amplía el dataset de paridad de `tests/Feature/TranslationsTest.php` si quieres que el
   test vigile también ese idioma.

## Nota: locale por usuario (no implementado)

Hoy el locale es global (`config/app.php`). Cuando haga falta por usuario, el camino es:

1. Columna `locale` en `users` + `App\Models\User implements HasLocalePreference` con
   `preferredLocale(): string` — con eso Laravel ya manda **notificaciones y mailables** en
   el idioma del usuario, sin más código.
2. Un middleware que haga `App::setLocale($request->user()?->locale ?? config('app.locale'))`
   registrado en `bootstrap/app.php`, dentro del grupo `web`.
3. Los componentes Livewire reciben el locale de la request, así que no necesitan nada
   extra; lo que sí hay que cuidar es **no cachear vistas o respuestas sin el locale en la
   clave**.

No lo implementes "por si acaso": mientras la app sea de un solo idioma, la config global
es suficiente y no hay estado que se pueda desincronizar.

## El test de cobertura

`tests/Feature/TranslationsTest.php` es lo que mantiene esto vivo:

| Test | Qué garantiza |
| --- | --- |
| claves `__()` traducidas | escanea `app/`, `resources/` y `routes/` (ignora `vendor/`, `node_modules/`, `*/Tests/`, `tests/e2e/`) y falla listando cada clave sin entrada en algún `en.json` (o en `lang/es.json` si el literal es inglés) |
| sin duplicados divergentes | una misma clave no puede traducirse distinto en dos JSON |
| paridad `es` ↔ `en` | `validation.php` recursivo (incluye `custom` y `attributes`), más `auth`, `passwords` y `pagination` |
| `__()` por locale | con `es` devuelve la clave, con `en` el inglés (incluidos placeholders) |
| validación en español | `Validator` real: `El campo correo electrónico debe ser…` |
| claves inglesas | las de Fortify y las del framework resuelven a español |
| correos del framework | renderiza `VerifyEmail` y comprueba que no queda ni un `Hello!` |

El escáner usa regex sobre `__('…')` / `__("…")`, con comillas escapadas contempladas. No
detecta `__($variable)`: si necesitas una clave dinámica, deja las literales visibles en
algún sitio (por ejemplo un `match` con los textos completos).

## Nombres de campo en los mensajes

`lang/es/validation.php` trae el bloque `attributes` con los campos reales del boilerplate
(`name` → *nombre*, `email` → *correo electrónico*, `password` → *contraseña*, `role` →
*rol*, `permissions` → *permisos*, `code`, `current_password`, `token`…), y `lang/en/`
mantiene las mismas claves. Por eso el error sale como
"El campo **correo electrónico** es obligatorio." y no "El campo email es obligatorio.".

Los Form Objects de Livewire (`Livewire\Form`) validan con las claves **sin** el prefijo
`form.` y sólo prefijan el error bag después, así que estos nombres planos sirven también
para `form.email`. Al añadir un campo nuevo a un CRUD, añade su nombre legible aquí.

## Comandos

```bash
# Republicar los archivos base de Laravel en inglés (tras actualizar el framework)
php artisan lang:publish

# Ver el locale efectivo
php artisan config:show app.locale
php artisan config:show app.fallback_locale

# El test de traducciones
./vendor/bin/pest tests/Feature/TranslationsTest.php

# Tras tocar config/app.php o .env en un entorno con caché
php artisan config:clear
```
